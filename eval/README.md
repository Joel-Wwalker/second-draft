# Evaluation batches

One paragraph proves nothing about a prompt change. This is how a change gets
judged on sixty.

The loop is split across node and a browser because the on-device model only
exists in a browser, while the prompt is built by the engine's own TypeScript and
must not be reimplemented anywhere.

## 1. Collect source paragraphs

AI-sounding text is the input a humanizer actually receives, so the sources are
generated by the same on-device model. In a page with the Prompt API available,
generate a paragraph per topic and save the array to `eval/sources.json` as
`[{ topic, text }]`.

## 2. Build the real prompts

    npm run eval:prompts

Reads `eval/sources.json`, runs each text through the engine's own
`buildSystemPrompt` and style measurements, and writes `eval/prompts.json` as
`[{ topic, input, systemPrompt }]`. This step exists so the batch tests the prompt
that ships, not a copy of it that has drifted.

## 3. Run them

Feed `eval/prompts.json` to the model in the browser and save
`[{ topic, input, output }]` to `eval/results.json`.

## 4. Read the result

    npm run eval eval/results.json

Reports how many inputs and outputs trip each signal, the mean spread and fronted
count either side, and every sample where the rewrite made a signal **worse** than
its input. That last list is the one that matters: it catches the model trading one
target for another, which is what happened when sentence length was the only thing
measured.
